六层 Draft，怎么逐层生成一块候选

对应当前归档的 packed Draft：C16 / cap192 / K15。蓝色主干逐层传递候选 hidden；绿色 context 分别送入六层；每层保存自己的 K/V。

一眼看全：六层串联 + 两条独立输入流

Target 的 8 个取样层先拼接、投影为同一份 context [1,16,2048]。候选块从 h₀ 走到 h₆；每层用自己的权重，从 context 和本层归一化 hidden 生成 K/V。

层间只有 hidden 串联： L0 的第二次 Add → L1 输入 → … → L5 的第二次 Add → 最终 Norm。没有第三次层间 Add。 context 不随层更新；present_k_i / present_v_i 在下一次调用回到同一个 i 层，不传给相邻层。

逐层展开：主干、Attention 和 MLP

六层拓扑相同、权重各自独立。点击层号或总览图中的层；L5 的可见性与前五层不同。

xᵢ = InputNormᵢ(hᵢ)
uᵢ = hᵢ + Oᵢ(Attentionᵢ(Qᵢ(xᵢ), K/Vᵢ(context, xᵢ), pastᵢ))
hᵢ₊₁ = uᵢ + Downᵢ(SiLU(Gateᵢ(PostNormᵢ(uᵢ))) × Upᵢ(PostNormᵢ(uᵢ)))

为什么最后一层不一样：候选块可见性

行是 Query，列是 Key。左侧将有效的 committed context 合成一列；右侧是 anchor + 15 个候选槽。L0–L4 的候选只能看自己和前面的有效槽；L5 可以看整个有效候选块。

蓝：候选 Key 可见绿：有效 context 可见橙：无效 Query 的 anchor 兜底灰：被 mask

这是源码 mask 的可视化，不执行模型。滑窗为 4096，当前最多 208 个位置，不触发窗口下界裁剪；前五层仍保留因果约束。

无效 Query 行仍保留计算，源码为其开放 anchor，避免整行 −∞。只有前 proposal_count 个候选输出被调用方消费。减小 proposal_count 不会缩小这个 K15 静态图。

本次 Draft 调用

12 份 past → 6 层各自更新 → 12 份 present。候选块的 K/V 仅参与本次 attention；输出的 15 个 token 是并行 proposal。

跨调用与 Target 验证

Target 验证 proposal 并决定接受前缀。后续从已提交位置的 Target 特征生成新增 context，更新对应 Draft KV；拒绝的候选不能直接成为 committed KV。

范围与源码

本页画的是 packed-spatial-host-embedding + CPU feature pack + StableArgMax 的六层逻辑数据流。算子内部融合、分区和精度以实际 AIR / OMC 为准。

归档 Draft 已有独立设备执行和约 60 ms 性能观测，原 CPU 数值门槛仍未通过。该 packed ABI 尚未替换旧 token-ID 常驻接口。本页不把结构节点着色为“精度通过”，也不把一次 profiling 当作完整 DFlash 验收。
